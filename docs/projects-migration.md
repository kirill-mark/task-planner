# Переход от разделов и групп к проектам

Макеты пакета B: один уровень «проект → задачи», проект необязателен,
«Входящие» — отдельный список неразобранного, а не «задачи без группы».
Здесь — как перевести на это данные так, чтобы ни одна задача не потерялась и
не сменила принадлежность. Ничего из этого ещё не сделано.

## Что сейчас в базе (20.10.2026, все аккаунты)

| | |
| --- | --- |
| Разделы (`mark_sections`) | 5 |
| Группы (`mark_groups`, у каждой `section_id`) | 16, из них 9 пустых (стартовые) |
| Задачи (не удалённые) | 118 |
| — без группы (сейчас это и есть «Входящие») | 75 |
| — без группы и без даты | 10 |
| Повтор названия группы внутри одного аккаунта | 1 случай |

## Принцип

Только добавление и переименование в интерфейсе, без переноса строк. Ни одна
задача не меняет `group_id`, ни одна строка не удаляется. Откат — вернуть
прежний интерфейс; данные для него остаются как были.

## Шаги

1. **Проект = существующая группа.** Таблица `mark_groups` остаётся, в
   интерфейсе её строки называются проектами. У задачи проект — прежний
   `group_id`. Задачи без группы — задачи без проекта. Принадлежность всех
   118 задач не меняется.
2. **Разделы не удаляются.** `section_id` у групп остаётся в базе (нужен для
   отката и экспорта), в интерфейсе не показывается. Новые проекты создаются
   без раздела — поле становится необязательным (`null`).
3. **Названия проектов.** Если название группы в аккаунте уникально — оно и
   есть название проекта. Если повторяется (1 случай) — к нему добавляется
   раздел: «KINOMARK · Продажи». Пользователь может переименовать.
4. **Пустые стартовые группы (9).** Не удаляются, а скрываются отметкой
   `archived_at` — их можно вернуть в списке проектов. Группа с хотя бы одной
   задачей (в том числе выполненной или в корзине) не скрывается.
5. **«Входящие» — отдельный признак.** У задачи появляется поле
   `inbox boolean`. Начальное значение:
   - нет группы, нет даты, не выполнена → `inbox = true` (10 задач);
   - всё остальное → `false`. 65 задач без группы, но с датой, сейчас
     числятся во «Входящих» лишь потому, что у них нет группы; после перехода
     они в плане по своим датам, без проекта, и не считаются неразобранными.
   «Готово» при разборе снимает `inbox`, не требуя ни даты, ни проекта.
6. **Совместимость со старыми клиентами.** Бот и веб-версия на `main` не знают
   про `inbox`. Серверный триггер при вставке ставит `inbox = true`, если у
   задачи нет ни группы, ни дат, — новые записи из бота попадут во «Входящие»
   как раньше. Контракт `mark_apply_operations` принимает новое поле, но не
   требует его.

## Проверка

Перед применением — резервная копия и снимок счётчиков по каждому аккаунту:
задачи по группам, задачи без группы, разделы. Миграция сначала прогоняется
в откатываемой транзакции и сверяется: число задач, их `group_id` и даты
совпадают до и после; `inbox = true` ровно у задач из правила выше. Затем —
на рабочей базе с той же сверкой и записью в `docs/deploys.md`.

## Что нужно решить

- Скрывать пустые стартовые группы или показать их как проекты.
- Нужны ли разделы как необязательные «папки» проектов позже, или их можно
  со временем убрать совсем (после окна отката).
