# MARK — ручная очистка корзины

9 октября: обе кнопки подготовлены и новая версия запущена на iPhone. «Убрать все» отправляет просроченные задачи в корзину; «Очистить корзину» требует подтверждения окончательного удаления. Клиентские проверки: 6/6, PostgreSQL: 12/12, UI: 12/12, движок: 21/21; сборка 14 ресурсов прошла. Выполнено только чтение живой схемы Supabase: нужные столбцы и функции есть, входящих FK на mark_tasks нет, триггер действует только при INSERT/UPDATE. Функция mark_mode в живой базе по умолчанию возвращает v2, поэтому миграция учитывает аккаунт без записи режима и создаёт epoch. Подготовлена миграция 0014_mark_empty_trash.sql; в рабочей базе она ещё не применена. Вход в Supabase выполнен; запрошено подтверждение включения функции, добавляющей право окончательно удалять только собственные задачи из подтверждённого снимка корзины. Установка функции сама строки не удаляет. Реальные данные агент не очищал. Подробности: MARK-iOS/docs/trash-cleanup.md.

Статус на 9 октября 2026: интерфейс и серверная миграция подготовлены; в рабочем Supabase миграция ещё не применена. Для продолжения нужен вход Кирилла в Supabase.

«Задачи → Просроченные → Убрать все» перемещает все просроченные задачи в корзину одним нажатием. Работает через существующую офлайн-очередь; поиск и пагинация не ограничивают очистку.

«Задачи → Корзина → Очистить корзину» показывает количество задач и предупреждение. Только после «Удалить окончательно» клиент синхронизирует очередь и вызывает mark_empty_trash. При отсутствии связи, смене аккаунта или отсутствующей серверной функции успешная очистка не показывается.

Серверная миграция: supabase/migrations/0014_mark_empty_trash.sql. Само применение миграции не удаляет строки. Функция берёт владельца из auth.uid(), проверяет ожидаемый аккаунт, блокирует запись владельца тем же механизмом, что обычные операции, и удаляет только строки с совпадающими id и deleted_at из подтверждённого снимка корзины. Активные, восстановленные и повторно удалённые позже задачи пропускаются. После удаления epoch аккаунта увеличивается, чтобы другие устройства взяли полный снимок. Транзакция откатывает удаление при любой ошибке. Функция не меняет группы, разделы, финансовое приложение или журнал операций; существующее хранение архивов не менялось.

Проверки: 21 проверка движка, 12 UI, 6 клиентских проверок корзины, 11 проверок PostgreSQL в изолированной PGlite 0.5.8. SQL проверен с реальной миграцией основной модели и исходными функциями mark_lock_user/mark_mode, но это не аудит живой схемы. В браузерном стенде на синтетических задачах проверены переход в корзину, окно подтверждения, отмена и очистка. Реальные задачи агент не удалял.

Для SQL-проверки отдельно установить @electric-sql/pglite@0.5.8 во временную папку и передать путь к модулю через MARK_PGLITE_MODULE при запуске scripts/test-empty-trash.mjs. Клиентские проверки: npm run test:trash.

Далее: войти в Supabase, прочитать текущую схему и зависимости функции; применить миграцию после согласования изменения серверных прав. Проверить наличие функции чтением, затем испытать окончательное удаление только на отдельной явно согласованной тестовой задаче. Для необратимого удаления реальных данных потребуется подтверждение пользователя непосредственно перед действием.
